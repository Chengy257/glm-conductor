# 运行细节

本文件是 glm-advisor 编排体系的运行细节文档，SKILL.md 与 role-contracts.md 之外的执行机制在此说明。

## 预检与生成

- 在 Agent 工具的可用类型列表中核对角色是否存在：delegate 需要 `glm-advisor:flash-implementer`，audit/full 需要 `glm-advisor:glm-reviewer`
- 缺失时的 fail-closed 处理：停止该通道，告知用户检查插件安装（Settings → Plugin Management），不得静默替换为其他子智能体类型
- 调用时不得附加模型/思考档位覆盖：GLM-5.3-Flash/high 与 GLM-5.3/max 已固定在子智能体定义中，任何运行时覆盖都会破坏本体系的风险分级假设

## 新鲜审查者语义

- ZCode 子智能体每次调用都是全新上下文，天然满足"新鲜审查者"要求：任何修复之后再次调用 reviewer，即得到未接触旧裁决的独立审查
- 审查者定义中模型固定为 GLM-5.3，与主会话同一旗舰模型；其独立性来自干净上下文与只读白名单，而非模型差异

## 验证证据

主会话的验证义务（不可由工作者报告替代）：

1. 亲自检查完整 diff（git diff 或逐文件读取），核对改动是否越界
2. 重跑 VERIFICATION 指定的全部命令
3. 将每条命令映射到主会话实际观察到的输出，之后才能交给审查者作为 VERIFICATION EVIDENCE

工作者的 IMPLEMENTATION REPORT 仅是声明，不是证据；证据只存在于主会话亲自观察到的 diff 与命令输出中。

## 修复与裁决失效流程

fix-first 之后必须按以下顺序执行（两种修正路径）：

1. **audit 路由**：主会话自行修正
2. **full 路由**：由原实施者（flash-implementer）修正
3. 主会话重跑全部验证命令，确认新证据
4. 换用全新 reviewer 复审（ZCode 子智能体天然新上下文，直接再次调用 `glm-advisor:glm-reviewer` 即可）
5. 旧裁决作废，不作为新审查的输入

rethink 裁决：修订架构后重新走对应路由，不得报告完成。

## 升级证据

可接受的升级触发：

- 新发现的复杂性（实现中暴露的隐藏依赖、意外的状态耦合）
- 新发现的风险（安全边界、数据破坏可能、生产影响）
- 宽影响面（改动波及规格外的共享文件）
- 误分类（实施者返回升级信号，声明任务实为判断密集/高风险）
- 审查者指出实质缺陷（rethink 或多项 fix-first）

不可接受的升级：无证据的直觉、想省事（例如把验证责任推给审查者）。每次升级必须在新的 SELECTIVE ROUTE 声明中附上新观察到的风险证据。

## 与 ZCode 机制的适配说明

- 子智能体内不能再派生子智能体，因此结构天然扁平：主会话是唯一编排者，任何嵌套编排设计在本体系中不可实现
- 子智能体只能看到主会话启动时已连接的 MCP 服务；会话中途新增的 MCP 服务对子智能体不可见
- 修改插件文件后需更新 marketplace 并新建会话才能生效；子智能体与技能的定义在会话启动时加载

## 故障处理

- **插件角色缺失**：Agent 工具可用类型列表中没有 `glm-advisor:glm-reviewer` 或 `glm-advisor:flash-implementer` 时，停止该通道，告知用户检查插件安装（Settings → Plugin Management），必要时重装后新建会话
- **模型名不符**：可用类型中的定义若显示非 `GLM-5.3-Flash` / `GLM-5.3`，视为名称不符，按 fail-closed 处理并告知用户，不得静默换用其他模型
- **审查者尝试越权写操作**：立即终止该通道，丢弃其全部输出，改用全新审查者重新审查；写入尝试本身记为审查通道的完整性事故
